## Доопрацювання другої ітерації (Усунення 404 при прямому відкритті та динамічний базовий шлях)

### 1. Усунення помилок 404 під час прямого відкриття вкладених сторінок
- **Проблема:** Браузерний спекулятивний сканер попереднього завантаження (HTML preload scanner Chromium) сканував відносні шляхи (`./root.css`, `./assets/...`) безпосередньо з HTML-розмітки ще до виконання інлайн-скриптів або застосування динамічного тега `<base>`. Внаслідок цього при прямому переході на вкладені маршрути (наприклад `/asd/sort/bubble` або `/sort/bubble`) браузер спершу надсилав 3 невдалі запити (`/asd/sort/root.css`, `/asd/sort/assets/...` або `/sort/root.css`, `/sort/assets/...`), отримував 404, і лише потім скрипт завантажував сторінку за виправленими шляхами.
- **Що змінено:**
  - У `vite.config.mts` додано плагін `dynamicBasePlugin` (стадія `transformIndexHtml`, `enforce: 'post'`, `apply: 'build'`). Плагін видаляє статичні теги `<link rel="stylesheet">` та `<script type="module">` із згенерованого `dist/index.html` і вбудовує синхронний завантажувач у `<head>`.
  - Завантажувач під час завантаження сторінки обчислює фактичний базовий шлях префікса (`/asd/sort/bubble` -> `/asd/`, `/qwe/sort/bubble` -> `/qwe/`, `/sort/bubble` -> `/`), динамічно підставляє `<base href="...">` та вставляє теги стилів і модульного скрипта з коректним базовим шляхом.
  - З `index.html` видалено старий інлайн-скрипт із жорстким рядком `/asd`.
  - Завдяки відсутності статичних відносних посилань у сирому HTML спекулятивний сканер браузера не генерує хибних запитів до підкаталогів маршрутів, і всі ресурси запитуються правильно з першого разу без жодного 404.
- **Як перевірено:**
  - Створено юніт-тест `src/tests/indexHtml.test.ts`, що верифікує структуру `dist/index.html` (відсутність статичних відносних ресурсів, наявність динамічного завантажувача, відсутність зашитих `/asd`).
  - Проведено тестування в реальному Chromium через Chrome DevTools Protocol (CDP) при статичній роздачі із SPA-fallback за 6 адресами: `/asd/sort/bubble`, `/asd/`, `/qwe/sort/bubble`, `/qwe/`, `/sort/bubble`, `/`. Зафіксовано 0 помилок 404 у мережевому журналі (всі ресурси повертають 200 OK) та коректний рендеринг вмісту в DOM.

### 2. Динамічне визначення базового шляху роутера (getRouterBasename) без прив'язки до `/asd`
- **Проблема:** У `src/App.tsx` функція `getRouterBasename()` перевіряла `pathname.startsWith("/asd")`, що працювало виключно для префікса `/asd` і ламало роботу застосунку при розгортанні під іншими префіксами (наприклад `/qwe/` або `/algo/`).
- **Що змінено:**
  - У `src/App.tsx` реалізовано динамічне визначення базового шляху під час виконання:
    1. Перевірка значення тега `<base>` (`document.querySelector("base")?.getAttribute("href")`).
    2. Перевірка `document.baseURI`.
    3. Визначення базового каталогу з адреси модуля скрипта бандла (`script[src*="/assets/"]`).
    4. Запасне зіставлення з кореневими сегментами маршрутів застосунку (`sort`, `search`, `ds`) для підтримки прямого рендерингу без окремого тега `<base>`.
  - У сирцевому коді застосунку (`src/App.tsx`, `index.html`, `vite.config.mts`) не залишилось жодної згадки рядка `/asd`.
- **Як перевірено:**
  - Оновлено та розширено тести в `src/tests/components.test.tsx` (`Router prefix and basename resolution (arbitrary prefixes and root)`):
    - динамічне визначення з тега `<base>` для `/qwe/`, `/algo/`, `/asd/`, `/`;
    - динамічне визначення з URL модуля скрипта;
    - динамічне визначення з довільних шляхів `pathname`;
    - рендеринг застосунку під довільним префіксом `/qwe/` та `/qwe/sort/bubble` без помилки 404.

### 3. Що не вдалося / Відхилені рішення
- Пряме звернення до `import.meta.url` у `src/App.tsx` викликало помилку завантаження модулів у Jest (`ts-jest`), який за замовчуванням виконує транспіляцію в CommonJS (`Must use import to load ES Module`). Замість прямих конструкцій `import.meta` в коді компонентів реалізовано універсальне визначення через `<base>`, `document.baseURI`, `script[src]` та аналіз шляхів маршрутизатора, що сумісно як з браузерним середовищем Vite (ESM), так і з тестовим середовищем Jest (CommonJS).
- Використання `document.write('<base href="...">')` не запобігає помилкам 404, оскільки фоновий попередній сканер Chromium ініціює мережеві запити до завершення виконання інлайн-скриптів. Повного усунення 404 досягнуто заміною статичних посилань на динамічну ініціалізацію ресурсів під час завантаження HTML.
